Terminal Rendering Capabilities

A 2026 field guide, weighted toward kitty (local), Windows Terminal (over SSH), and xterm.js.

Your mental model — 16 colours, a handful of character sets, a cursor — was accurate for about twenty-five years. It stopped being accurate around 2017, and the pace has picked up sharply since 2022. The short version: character sets are a solved and dead topic, colour went to 24-bit and stayed there, and the genuinely new capabilities are in text decoration, frame synchronisation, keyboard fidelity, and clipboard access — not in graphics, which remains fragmented.

The headline for SSG: three features are supported on all three of your platforms today, need no capability negotiation, degrade silently where absent, and each maps onto something SSG already has but cannot express. They are styled underlines (SSG has LSP diagnostics and no way to draw a squiggle), synchronized output (SSG redraws whole frames), and OSC 52 clipboard (SSG has a clipboard register that cannot reach Windows when you are on SSH).

1. Colour — where 24-bit actually landed

Your model is right, and the tiers stack rather than replace each other. All three of your platforms support all three tiers.

TierSequenceSpaceNotes
ANSI 16ESC[30–37m / 90–97m8 + 8 brightThe only tier the user's theme controls. Still the safest floor.
Indexed 256ESC[38;5;nm16 + 6×6×6 cube + 24 greysUniversal since the 2000s. The cube is not perceptually uniform.
TruecolorESC[38;2;r;g;bm24-bit, 16.7MYes — 24-bit, as you assumed. Universal on modern terminals.

The one subtlety worth knowing

There are two syntaxes. The semicolon form 38;2;r;g;b is what everyone actually uses and what SSG emits. The spec-correct form uses colons (38:2::r:g:b), because r/g/b are sub-parameters of the colour, not siblings of it. Both work everywhere you care about for SGR 38/48.

This matters later: for the newer attributes — styled underlines and underline colour — the colon form is the canonical one, and it is the form you should emit.

Detection. There is no reliable escape-sequence query for truecolor. The convention is the COLORTERM environment variable being truecolor or 24bit. It does not survive sudo or some SSH configurations, which is why SSG's existing ColorDepth fallback chain (env → TERM hints → assume truecolor) is the right shape.

2. Character sets — why the question dissolved

This is the part of your model that has changed the most, and the change is that the problem went away and was replaced by a harder one.

What died

The DEC charset machinery — ESC ( 0 to switch G0 into the line-drawing set, SO/SI shifting between G0 and G1, national replacement character sets — is legacy. Terminals still parse it (which is exactly why an escape sequence smuggled into a glyph could wreck SSG's display before it was fixed), but nothing should emit it. Box drawing is done with real Unicode: │ ├ ─ ┼ ╭ ╯.

CP-437 is a DOS-era artefact. It survives culturally — in ANSI art and in the aesthetics of retro-styled TUIs — but not as a wire encoding. UTF-8 won completely. There is no second widespread encoding you are unaware of; that is genuinely the whole answer.

What replaced it, and it is harder

Once everything is UTF-8, the hard question stops being "which byte means which glyph" and becomes "how many columns does this occupy, and where can I split it":

  • Grapheme clusters (UAX #29) — é may be one code point or two; a family emoji may be seven joined by ZWJ; a flag is two regional indicators. All are one character to a user.
  • East Asian Width (UAX #11) — CJK and most emoji occupy two columns. Get this wrong and every subsequent cell on the row is misaligned.
  • Ambiguous width — a residual class where terminals genuinely disagree.

SSG is already ahead here. GraphemeLayout implements UAX #29 segmentation and UAX #11 widths against Unicode 15.0, classifies C0/C1/DEL as Control, and gives invalid UTF-8 a visible replacement glyph. That is the correct modern answer, and most TUI toolkits do it worse.

One emerging thing: DEC mode 2027 asks the terminal to do grapheme clustering itself rather than counting code points. kitty and ghostty support it. It is worth knowing about but not worth adopting — SSG already computes authoritative widths, and mode 2027 mainly helps applications that do not.

3. Cursor control

More control than you might expect, and all of it is well supported.

ControlSequenceEffect
PositionESC[row;colH1-based. SSG uses this each frame to park the caret.
VisibilityESC[?25h / ?25lDECTCEM. Hide during redraw, show after.
ShapeESC[n qDECSCUSR — see below.
ColourOSC 12 ; colour STSet cursor colour; OSC 112 resets. Widely supported.
Save / restoreESC 7 / ESC 8Position + attributes. Rarely needed in a full-redraw app.

DECSCUSR shapes — 0/1 blinking block, 2 steady block, 3 blinking underline, 4 steady underline, 5 blinking bar, 6 steady bar. SSG uses 5, and correctly resets to 0 on exit — that reset is what stops your shell inheriting a bar cursor after ssg quits.

A genuinely useful trick most editors miss: change the cursor shape with the editing mode. Block for a normal/command mode, bar for insert, underline for replace. It costs one escape sequence and communicates modal state better than any status line.

4. Underlines & text decoration Top pick for SSG

This is the feature you saw in those TUI videos, and it is far more capable than plain underline. It began as a kitty extension and is now supported by essentially every terminal that matters.

const recieve = fn(); ← curly, red — a spelling/LSP error
let unused = 42; ← dotted, yellow — a warning
type Handle = u32; ← double, green — a definition

The two sequences

ESC[4:0m   none          ESC[4:3m   curly  ← the squiggle
ESC[4:1m   single        ESC[4:4m   dotted
ESC[4:2m   double        ESC[4:5m   dashed

ESC[58:2::r:g:bm   underline colour, independent of the text colour
ESC[59m               reset underline colour to follow the foreground

The second is the important half. The underline carries its own colour, so a red squiggle can sit under text that keeps its syntax highlighting. Without SGR 58 you would have to recolour the text to signal an error, which destroys the highlighting.

xterm.jsYes — all fiveYesCore feature since v5.0 (2022). No addon needed.

Verdict: adopt unconditionally. Supported on all three of your platforms. Use the colon form. Avoid legacy SGR 21 for double underline — it is ambiguous and xterm.js does not implement it.

The cost is not the escape sequence — it is the cell model. SSG's CellGridCell currently carries foreground, background, role and tint. Underline style and underline colour are two more per-cell attributes, which widens the cell and the frame encoder's attribute-change comparison. That is the real design decision, and it is worth a spec rather than a patch.

5. Synchronized output Top pick for SSG

The least glamorous feature here and possibly the highest value for SSG specifically, because SSG redraws the entire screen every frame.

ESC[?2026h   begin — terminal keeps parsing, stops painting
   ... one complete frame ...
ESC[?2026l   end — terminal paints the final state, once

Without it, a large frame can be painted while it is still arriving, so the user sees a partial update — tearing, or a visible sweep down the screen. This is worst exactly where it is most annoying: over SSH, where the frame arrives in TCP-sized pieces.

TerminalMode 2026Notes
kittyYesComprehensive.
Windows TerminalYesHas an anti-spam guard so a misbehaving app cannot stall the renderer.
xterm.jsYes, v6.0+ — with live bugsSee warning below.
ghostty / WezTerm / foot / Alacritty / iTerm2 / KonsoleYes

xterm.js has two open bugs that hit full-frame redraw apps specifically. (1) ESC[2J inside a synchronized block still yanks the viewport to the bottom — this is the reported cause of scroll-jank with CLI agents in VS Code's terminal. (2) Continuous animation can be capped at roughly 1 fps, because the next begin resets the render debouncer before the previous end has painted.

Mitigation: do not clear inside the block, and make each frame exactly one begin/end pair rather than nesting or leaving one open across frames.

Verdict: adopt, carefully. Unknown DEC private modes are silently ignored per ECMA-48, so emitting this on a terminal that lacks it costs nothing and produces no garbage. It is safe to send unconditionally — no detection required.

6. Hyperlinks (OSC 8)

Arbitrary text can be a clickable link, independent of whether it looks like a URL.

ESC]8;;https://example.com ESC\  link text  ESC]8;; ESC\
ESC]8;id=err1;file:///path/to/main.cpp ESC\  main.cpp:42:7  ESC]8;; ESC\

Supported on all three of your platforms, plus ghostty, WezTerm, foot, Alacritty, iTerm2, Konsole, and GNOME Terminal. Both BEL and ESC \ terminators are accepted; prefer ESC \. The optional id= parameter groups a link that wraps across lines, though xterm.js does not yet unify the highlight for those.

Windows Terminal caveat for your SSH workflow: a file:// link resolves on the Windows side, so a path on this Linux box will not open. Useful for https:// documentation links; not useful for jumping to a local file. That jump should stay an internal SSG command.

Verdict: nice-to-have. Genuinely useful for LSP diagnostic codes linking to documentation, and for URLs in file content. Not transformative.

7. Keyboard protocols Newly viable

The biggest surprise in this research, and it directly contradicts what I would have told you a year ago.

Terminals have always sent keys as an ambiguous byte soup: Ctrl+I and Tab are both 0x09. Ctrl+M and Enter are both 0x0D. Ctrl+[ and Escape are both 0x1B. There are no key-release events, and many modifier combinations are simply unrepresentable.

The kitty keyboard protocol fixes all of that, with per-feature opt-in:

ESC[>1u    disambiguate — Ctrl+I ≠ Tab, Ctrl+M ≠ Enter, Ctrl+[ ≠ Escape
ESC[>3u    ... plus press / repeat / release event types
ESC[<u     pop back to the previous mode on exit
TerminalSupportNotes
kittyFullReference implementation.
Windows TerminalPreview only — v1.25Merged Feb 2026, but v1.25 is still preview; the current stable release (1.24) does not implement it. Verified 2026-07 against WT 1.24 over ssh: it answers DECRQM and DA1 but returns nothing at all to CSI ? u. Known bugs remain around F13–F20 and non-Latin layouts.
xterm.jsImplemented, active bugsLayout awareness incomplete; test before relying on it.
ghostty / footFull
WezTermFull but opt-inenable_kitty_keyboard = true, default off.
AlacrittyMostlySome modifier-bit discrepancies.
xterm properNoUses modifyOtherKeys instead.

Why this matters for SSG specifically. SSG's keymap is chord-based with an Escape leader — a design partly forced by this ambiguity, since Ctrl combinations collide with control characters and cannot be told apart. With this protocol the keyspace roughly triples, and Ctrl chords become bindable without collision.

The catch: it changes what the decoder receives, so it is a decoder change, not a config flag. And modifyOtherKeys — the older xterm fallback — is not supported by Windows Terminal, so there is no useful middle tier. It is this protocol or the legacy encoding.

Two smaller input features worth having

  • Bracketed paste (ESC[?2004h) — universal, no exceptions. Pasted text arrives wrapped in ESC[200~ … ESC[201~ so an editor can tell paste from typing. Without it, pasting into an editor with auto-indent produces the classic staircase.
  • Focus events (ESC[?1004h) — universal. The terminal reports focus gained/lost. Useful for pausing a blinking cursor, or triggering an external-modification check when the user returns.

8. Clipboard — OSC 52 Matters most for your SSH workflow

An application can put text on the local system clipboard by emitting an escape sequence, even when it is running on a remote machine. For your Windows-Terminal-over-SSH setup this is the only mechanism that exists — there is no other route from a process on this box to the Windows clipboard.

ESC]52;c;<base64 payload>ESC\      write to the system clipboard
ESC]52;c;?ESC\                     request the clipboard contents
TerminalWrite (copy)Read (paste)Notes
kittyYesYes~1 MB practical payload limit.
Windows TerminalYes — since v1.1 (2020)No — deliberateRead was refused on security grounds: an app could exfiltrate the clipboard silently. Write is focus-gated since v1.25.
xterm.jsYes, via addonHost-dependent@xterm/addon-clipboard; has an open UTF-8 bug.
ghostty / WezTerm / iTerm2YesYes
foot / Alacritty / KonsoleYesOff by defaultRead is opt-in for the same security reason.

Verdict: adopt write; do not design around read. Copy-to-local-clipboard works on all three platforms. Read is not available on Windows Terminal and never will be, so a design that depends on pulling the system clipboard will not work for your primary remote setup. Paste should continue to arrive through bracketed paste — which is the terminal pasting into you, and works everywhere.

tmux intercepts OSC 52. If you use tmux, you need set -g allow-passthrough on (tmux ≥ 3.3) or set -g set-clipboard on, or the sequence dies at the multiplexer and never reaches Windows Terminal.

Also note an open Windows Terminal deadlock bug triggered by rapid OSC 52 writes combined with mouse interaction — so rate-limit clipboard writes rather than emitting one per keystroke.

9. Images — sixel vs the kitty graphics protocol

Your read is correct on both counts: sixel is clunky, the kitty protocol is markedly better, and Windows Terminal does not support the kitty protocol.

Sixel

A DEC format from the 1980s: bitmap data encoded as printable characters, six vertical pixels per character. Palette-based and verbose.

Your instinct about variable cell sizes is right, and here is the precise answer: an application must ask the terminal how big a cell is, in pixels, before it can size an image to fit a grid region:

ESC[16t   →  ESC[6;height;widtht     cell size in pixels — ask this first
ESC[14t   →  ESC[4;h_px;w_pxt        text area in pixels — divide by rows/cols
ioctl TIOCGWINSZ → ws_xpixel / ws_ypixel   often zero; VTE never fills it in

So it is worse than clunky — it requires a round trip query before you can lay anything out, and a fallback path for terminals that answer with zeros.

The kitty graphics protocol

Designed for exactly the problem you identified. Its decisive advantage for a grid-based editor: you place an image in cell coordinates — "occupy this 20×10 rectangle of the grid" — and the terminal handles scaling. No pixel arithmetic, no query round trip. It also has image IDs and reuse, z-index so text can layer over images, transfer via file or shared memory instead of a giant escape payload, and unicode placeholders — a mechanism that lets images survive scrolling and pass through multiplexers, because the image position is anchored to actual grid cells.

Verdict for SSG: do not build on this. There is no image protocol that works across your three platforms without user opt-in. Sixel has the widest raw reach, but VS Code ships xterm.js's image addon disabled by default, and the kitty protocol is blocked entirely by Windows Terminal with no timeline.

Images in a terminal are a kitty-and-friends progressive enhancement, not a foundation. For a text editor the honest assessment is that the cost — a capability-detection path, two protocol encoders, a pixel-geometry fallback, and a degraded mode that has to look deliberate rather than broken — buys very little that a text editor actually needs.

10. Capability detection without hanging

The obvious approach — send a query, wait for a reply — deadlocks on any terminal that ignores the query. There is a standard trick.

The DA1 fence

Primary Device Attributes (ESC[c) is answered by every terminal. So send your speculative query first, then DA1, then read until you see the DA1 reply. If the speculative answer arrived before it, the feature exists. If only DA1 came back, it does not — and you never block, because DA1 always answers.

write("ESC[?u")   // does the terminal support the keyboard protocol?
write("ESC[c")    // fence — always answered
// read until the DA1 reply arrives; a ?u reply before it means yes
QueryUseReliability
ESC[c — DA1The fence; also advertises OSC 52 via extension 52Universal
ESC[?n$p — DECRQMQuery a specific private mode (e.g. 2026)Best general mechanism
ESC[>0q — XTVERSIONTerminal name and versionWindows Terminal does not implement it
ESC[16tCell size in pixelsNeeded only for images
$COLORTERMTruecolorConvention; lost across sudo/SSH

DECRQM replies: 0 not recognised, 1 set, 2 supported but reset, 4 permanently reset. So 1 or 2 means the feature exists.

The cheerful conclusion: for the three features SSG should actually adopt, you do not need any of this. Styled underlines, synchronized output and OSC 52 write all degrade silently to nothing on a terminal that lacks them. Detection only becomes necessary for the keyboard protocol (which changes input parsing) and images (which you should skip).

If you take one thing: #1 and #2 together are a small, low-risk change that makes SSG visibly better on every platform you use — diagnostics you can actually see, and a frame that never tears over SSH. Neither needs capability detection, and both degrade to nothing on a terminal that lacks them.

There is also a pleasing symmetry: the escape-discipline work already landed gives SSG a mode stack where adding a mode means declaring its entry and exit together. Synchronized output is a frame-scoped mode — precisely the shape that infrastructure was built for.
