# spec-unicode-gcb-state-machine

## Goals

Replace the ad-hoc property predicates in `src/layout.cpp` with an exact Unicode 15.0.0
UAX #29 Grapheme_Cluster_Break (GCB) property state machine derived from the official
`GraphemeBreakProperty.txt`. Fix two known GB11 bugs exposed by the oracle. Pin the
three canonical Unicode 15.0.0 data files (`GraphemeBreakProperty.txt`,
`emoji-data.txt`, `GraphemeBreakTest.txt`) in `data/unicode/`. Add a
`GraphemeBreakTest.txt` oracle test and adversarial fixtures that cover the bugs and
boundary cases the hand-authored suite misses. Separate display-width determination
into a dedicated pure function.

After this change:
- Every GCB segmentation decision traces to an explicit `GcbProp` enum value derived
  from the official file.
- The GraphemeBreakTest.txt oracle passes all 473 applicable cases; its parser
  excludes 129 CR/LF cases under the stated logical-line precondition.
- Two known GB11 correctness bugs are fixed and covered by adversarial fixtures.
- `display_width_of(cp, gcb)` is an explicit, separately callable function.

## Design

### GcbProp enum and unified k_gcb table

Mechanism: replace the four ad-hoc tables (`k_combining`, `k_spacing_mark`, `k_prepend`,
and the five Hangul predicates) with a single `GcbRange { lo, hi, GcbProp }` array
`k_gcb[]` sorted by `lo`. `gcb_prop_of(cp)` binary-searches this table and returns the
matching `GcbProp`; code points not listed return `GcbProp::Other`.

`GcbProp` enum values (exactly the UAX #29 GCB property values):
`Other, CR, LF, Control, Extend, ZWJ, SpacingMark, L, V, T, LV, LVT, Prepend, RI`.

LV and LVT syllables (AC00–D7A3, ~1 176 individual/range entries in the official file)
are NOT stored in `k_gcb`; they are computed by `(cp - 0xAC00) % 28 == 0` (LV) or
`!= 0` (LVT). `gcb_prop_of` handles this before the binary search. This avoids
~1 200 extra table entries while remaining exact.

`k_gcb` is generated by `tools/gen_gcb_table.py` from the pinned
`data/unicode/GraphemeBreakProperty.txt`. The generated table replaces the content of
the four existing tables and all five Hangul predicates (`is_hangul_l/v/t/lv/lvt`).

`k_extpic` (Extended_Pictographic, from `emoji-data.txt`) and `k_wide`
(EAW=W/F, from `EastAsianWidth.txt` + `emoji-data.txt`) are retained unchanged; they
are not GCB properties and are needed for display-width.

### Control code points outside C0/C1

The official `GraphemeBreakProperty.txt` assigns `GcbProp::Control` to code points
beyond the ASCII C0/C1 ranges, including: `00AD` (Soft Hyphen), `200B` (ZWSP),
`200E–200F` (directional marks), `2028–2029` (line/paragraph separators),
`202A–202E` (bidi embedding controls), `2060–206F` (word joiner and format chars),
`FEFF` (BOM), `FFF0–FFF8`. These are currently in `k_combining` (treated as
GCB=Extend) — a correctness error. In the refactored code `gcb_prop_of` returns
`GcbProp::Control` for them; `compute_cell_run` treats them as `kind=control`.
However, unlike C0/C1 which produce visible replacement glyphs (`width=1`), these
non-C0/C1 GCB=Control code points are Unicode Cf format characters with `width=0`.
They break as their own cluster (segmentation is correct per GCB=Control) but occupy
no terminal column. C0 (U+0000–U+001F), DEL (U+007F), and C1 (U+0080–U+009F) keep
`width=1`.

`200C` (ZWNJ) is `GcbProp::Extend` per the official file; it remains absorbed. `200D`
(ZWJ) is `GcbProp::ZWJ`; it is absorbed by GB9 but tracked separately in the GB11
state machine (see below).

### GB11 state machine (bug fix)

Two bugs in the current `after_zwj` tracking:

Bug 1 — lone ZWJ base: `bool after_zwj = (cp == 0x200Du)` arms GB11 when the cluster
BASE is ZWJ. GB11 requires `ExtPic Extend* ZWJ × ExtPic`; a lone ZWJ has no preceding
ExtPic. A following ExtPic should start a new cluster.

Bug 2 — consecutive ZWJs: when two ZWJs are absorbed into an ExtPic cluster, the second
ZWJ re-arms `after_zwj`. But `ExtPic ZWJ ZWJ` does NOT match `ExtPic Extend* ZWJ`
because GCB=ZWJ ≠ GCB=Extend; the second ZWJ is not in `Extend*`.

Fix: replace `after_zwj` with a three-value `GB11State` enum:
- `None` — not in an ExtPic cluster or pattern broken
- `ExtPic` — cluster base is ExtPic (or another ExtPic joined via GB11), may have Extends
- `Zwj` — ExtPic Extend* ZWJ matched; next ExtPic will be absorbed by GB11

State transitions (on each absorbed code point inside the extension loop):

When absorbed via GB9 (GcbProp::Extend or GcbProp::ZWJ):
- `None` + Extend → `None`
- `ExtPic` + Extend → `ExtPic` (Extend* grows)
- `Zwj` + Extend → `None` (Extend after ZWJ is not ExtPic; pattern abandoned)
- `None` + ZWJ → `None`
- `ExtPic` + ZWJ → `Zwj` (ZWJ after ExtPic Extend*, pattern complete)
- `Zwj` + ZWJ → `None` (second ZWJ: GCB=ZWJ ≠ GCB=Extend, not in Extend*; pattern broken)

When absorbed via GB9a (GcbProp::SpacingMark):
- `ExtPic` + SpacingMark → `None` (SpacingMark ≠ Extend, breaks ExtPic Extend* chain)
- `Zwj` + SpacingMark → `None`
- `None` + SpacingMark → `None`

GB11 absorption fires only when `gb11 == Zwj` and `is_extended_pictographic(ext_cp)`.
On GB11 absorption → new state = `ExtPic` (chain continues).

Initial value: `GB11State::ExtPic` if `is_extended_pictographic(cp)`, else `GB11State::None`.

### Separated display_width_of

Mechanism: `static uint32_t display_width_of(uint32_t cp, GcbProp gcb) noexcept` is
a pure function (no side effects, no access to clustering state) that returns `0`, `1`,
or `2`. Rules:

- `GcbProp::Extend`: `is_wide(cp) ? 2 : 0`. Wide emoji modifiers (U+1F3FB–U+1F3FF,
  EAW=W) return 2 when standalone; all other Extend (diacritics, VS, ZWNJ) return 0.
- `GcbProp::ZWJ`, `SpacingMark`, `Prepend`: `0`.
- `GcbProp::Control` + C0/DEL/C1 (cp ≤ U+009F): `1` (visible replacement glyph).
- `GcbProp::Control` + non-C0/C1 (cp > U+009F): `0` (Unicode Cf format character).
- `GcbProp::CR`, `LF`: `0` (line terminators forbidden in compute_cell_run input).
- All other GcbProp values (`L`, `V`, `T`, `LV`, `LVT`, `RI`, `Other`): `is_wide(cp) ? 2 : 1`

Note: V jamo (1160–11A7) and T jamo (11A8–11FF) have EAW=Neutral (not W) per
`EastAsianWidth.txt`; they are NOT in `k_wide` and return 1. L jamo (1100–115F,
A960–A97C), LV/LVT syllables (AC00–D7A3), and RI (1F1E0–1F1FF) are in `k_wide`
and return 2. `display_width_of` uses `is_wide(cp)` for all non-combining non-control
code points; no special casing of Hangul or RI is required.

### GraphemeBreakTest oracle

Mechanism: `tests/test_gcb_oracle.cpp` reads the pinned
`data/unicode/GraphemeBreakTest.txt` at runtime (path supplied via CMake compile
definition `UNICODE_DATA_DIR`). For each test line:
1. Parse the hex code points and break markers (÷ / ×).
2. Skip any line where any code point is `000D` (CR) or `000A` (LF). Reason: GB3/GB4/GB5
   apply to CR and LF; `compute_cell_run` requires no-CR/LF input by precondition.
3. UTF-8 encode the code point sequence.
4. Call `compute_cell_run`.
5. Assert span count equals the number of clusters in the test case (number of ÷-separated
   groups, excluding the leading ÷).
6. Assert each span's `byte_offset + byte_len` equals the cumulative byte length of the
   corresponding cluster's code points.

Failure output names the test-file line number and the offending case.

### Official data files

Three files pinned from `https://unicode.org/Public/15.0.0/ucd/auxiliary/`:
- `data/unicode/GraphemeBreakProperty.txt` — authoritative GCB property source
- `data/unicode/GraphemeBreakTest.txt` — oracle test cases
And from `https://unicode.org/Public/15.0.0/ucd/emoji/`:
- `data/unicode/emoji-data.txt` — Extended_Pictographic and emoji presentation data

`data/unicode/README.md` is updated to document all five files, pinned URLs, and the
generator script.

### Generator script

`tools/gen_gcb_table.py` reads `data/unicode/GraphemeBreakProperty.txt` and outputs
the `k_gcb[]` C++ array to stdout. LV and LVT are excluded from the output. Running the
script reproduces the table currently embedded in `src/layout.cpp`.

## Invariants

I7 from `doc/spec.md`: layout is deterministic and renderer-neutral.
The public `compute_cell_run` signature is unchanged.

## Considerations

- **Hangul V/T width**: V jamo (1160–11A7) and T jamo (11A8–11FF) have EAW=Neutral;
  they are NOT in `k_wide`. `display_width_of` returns 1 for them via `is_wide(cp) = false`.
  No existing fixture tests standalone V or T jamo.
- **GCB=Control in extension loop**: GcbProp::Control candidates in the extension loop
  fall through to "no extension" → break the cluster. This is correct per GB4/GB5.
  GB9b check is updated: `is_gcb_ctrl = (ext_gcb == GcbProp::Control || …CR || …LF)`.
- **SpacingMark and GB11**: SpacingMark (GB9a: × SpacingMark) absorbed by GB9a. It is
  not in `Extend*` per GB11 (`Extend*` requires GcbProp::Extend). If SpacingMark is
  absorbed while in `GB11State::Zwj`, state → `None`.
- **LVT range check**: `gcb_prop_of` uses `(cp - 0xAC00) % 28` only for `AC00–D7A3`.
  Hangul Extended-B LV/LVT in `D7B0–D7FB` are listed in `GraphemeBreakProperty.txt` as
  V (D7B0–D7C6) and T (D7CB–D7FB), not LV/LVT, so the computation range is exactly
  `AC00–D7A3`.

## Risks and Mitigations

- **Table generation correctness**: the generator script is checked in and its output is
  verified by running it and diffing against the embedded table during CI. The
  GraphemeBreakTest oracle independently validates every row.
- **Performance regression**: the unified `k_gcb` table is larger than individual tables
  but the binary search is O(log n) over one array vs. multiple independent searches; the
  net effect is neutral to slightly better due to cache locality.
